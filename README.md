# OpenSIEM-AI — Reproducible Open-Source SIEM with ML Detection and SOAR Response

Code, datasets, and experiment scripts for the paper *OpenSIEM-AI: A Reproducible Open-Source Reference Architecture for ML-Driven SIEM and Automated SOAR Containment* (Radid, Ghazouani & Benlahmar, 2026). Each experimental result in the paper is regenerated by one of the numbered scripts below; the mapping from table/figure to script is given in the next section.

Released under the Apache-2.0 license.

## One-time setup

Requirements:

- Python 3.9+ (Apple Silicon arm64 tested; libomp is required for XGBoost and must be installed separately, e.g. `brew install libomp`, then point `DYLD_LIBRARY_PATH` at it)
- Docker Desktop 4.74+ for the streaming benchmark (8 GB RAM allocated to Docker is enough)
- A Kaggle account with API token at `~/.kaggle/kaggle.json` (used by scripts 01, 02, 03 and 06 to download NSL-KDD, GUIDE, HDFS LogHub and UNSW-NB15)

```bash
git clone https://github.com/aliradid/siem-ai.git
cd siem-ai
bash scripts/setup.sh
source .venv/bin/activate
```

## Reproducing the paper, in order

### Phase 1 — Offline detection (≈ 2.5 h total, one-time)

```bash
# 1. NSL-KDD — XGBoost binary normal-vs-attack (≈ 5 min)
DYLD_LIBRARY_PATH=.venv/lib/libomp python scripts/01_train_nsl_kdd.py
# → results/nsl_kdd_metrics_proper.json   (acc 0.7756, F1 0.7748, ROC AUC 0.9694
#   on the canonical KDDTrain+ → KDDTest+ benchmark protocol)

# 2. Microsoft GUIDE — XGBoost 3-class incident triage (3 000 boosting rounds, downloads ~600 MB)
DYLD_LIBRARY_PATH=.venv/lib/libomp python scripts/02_train_guide.py
# → results/guide_metrics.json     (acc 0.7214, macro F1 0.6797)

# 3. HDFS LogHub — Bi-LSTM binary anomaly detection (≈ 100 min, downloads ~1.6 GB)
python scripts/03_train_hdfs.py
# → results/hdfs_metrics.json      (acc 0.9994, macro F1 0.9945)
```

### Phase 2 — Streaming + SOAR (≈ 5 min total once Docker is up)

```bash
# 1. Bring up the stack (Elasticsearch + Kafka + Logstash + ML inference + Prometheus)
cd docker && docker compose up -d && cd ..

# 2. Verify health
curl http://localhost:5001/healthz   # {"status":"ok",...}
curl http://localhost:9200           # ES cluster info

# 3. Install the ES index template (one-time, picks up float type for features)
curl -X PUT -H "Content-Type: application/json" http://localhost:9200/_index_template/siemai-events -d @docker/es-template.json

# 4. Streaming benchmark
python scripts/04_streaming_benchmark.py --rate 100 --duration 15 --n-events 500
# → results/streaming_benchmark.json     (single-run p50/p95/p99 ingest-to-ML-verdict;
#   the timestamp is taken in the Logstash filter stage, before Elasticsearch)
# For the 5-rep means at 100/250/500/1000 eps used in Table 11 see
#   results/stress_test_reps.json.

# 5. SOAR validation (real iptables DROP when run as root; real TheHive case when
#    THEHIVE_URL + THEHIVE_API_KEY are set; Azure AD disable is a simulated stub)
sudo THEHIVE_URL=... THEHIVE_API_KEY=... python scripts/05_soar_validation.py --cycles 500
# → results/soar_validation.json       (p95 ingest-to-containment 1.16 s over 500 cycles)
```

## Hardware reproducibility

All numbers in the paper were measured on a 14-core Apple Silicon Mac (CPU-only TensorFlow, single-node Docker Desktop, 8 GB Docker RAM allocation). The streaming p95 latencies will differ on other hardware — re-run `04` and `05` on your target environment and report the new numbers.

## Known limitations

- The streaming benchmark uses an HTTP input on Logstash (port 8080), not Filebeat → Kafka. Throughput numbers therefore reflect the ML inference + Elasticsearch path, not the full Filebeat tail.
- SOAR playbooks run against real targets where the environment allows: `play_iptables_drop` issues a real netfilter rule when the harness runs as root, and `play_thehive_case` posts to a live TheHive instance when `THEHIVE_URL` and `THEHIVE_API_KEY` are set; each falls back to a timed stub otherwise. `play_account_disable` (Azure AD) is always a simulated stub modelling one Graph API round-trip. The published numbers were measured with the two real paths active.
- Wazuh Active Response is described in the paper but is not part of `docker-compose.yml` due to its memory footprint; see `docker/README-wazuh.md` for the bring-up procedure.
